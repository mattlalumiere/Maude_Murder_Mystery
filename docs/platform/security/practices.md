# Security practices

Owner: W10. Code that implements parts of this lives in `web/src/lib/security/**` and `web/src/middleware.ts`.

## 1. Secrets handling

Secrets: `AUTH_SECRET`, OAuth client secrets (`AUTH_GOOGLE_SECRET` and friends), `DATABASE_URL` password, S3 keys (only when not using workload identity), `AI_API_KEY`, per game override hash salts (not secret but private), `K_cell` (tenancy.md).

Rules:
1. No secret in the repo, in an image layer, in a Helm values file committed to git, in `docker-compose.yml`, or in a build arg. `web/.env.example` holds names and dummy values only.
2. Local: `deploy/local/.env` is git-ignored and generated by `make up` on first run (random `AUTH_SECRET`). Never reuse it elsewhere.
3. Cloud: an external secret store (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) synced by the External Secrets Operator or mounted by the CSI driver into the pod as env or files. The chart takes a secret **name**, never a value.
4. Prefer workload identity (IRSA, Azure Workload Identity, GKE Workload Identity) over long lived keys for S3 and DB.
5. Rotation: `AUTH_SECRET` supports a list (`AUTH_SECRET` plus old one in Auth.js rotation) every 90 days; DB password every 90 days with dual-user swap; OAuth secrets yearly or on staff change; `AI_API_KEY` on suspicion. Rotation is a deploy of config, not code.
6. Detection: gitleaks (or trufflehog) pre-commit and in CI over the full history; image scan for high-entropy strings; CI fails on a hit.
7. Process env is not logged. The logger redacts `DATABASE_URL` and key-shaped names (`logger.ts`).
8. Secrets are never passed to the model, never placed in prompts, never echoed in error messages.

## 2. Authn and authz matrix

Roles: **anon** (no credentials), **screen** (anon with a code), **player** (id + token), **host** (Auth.js session whose id equals `room.hostId`), **operator** (cluster admin, not an app role).

| Endpoint | anon | screen | player | host | Notes |
|---|---|---|---|---|---|
| `GET /api/healthz`, `/api/readyz` | yes | | | | never rate limited, no secrets |
| `/api/auth/*` | yes | | | | Auth.js; `auth` bucket 10 per IP burst |
| `POST /api/rooms` | no | | | yes (signed in) | `create` bucket; quota per host (planned) |
| `POST /api/rooms/{code}/join` | yes | | | | knowing the code is the credential; `join` bucket |
| `GET /api/rooms/{code}/state` (screen) | yes | yes | | | `publicView` only |
| `GET .../state?role=player` | no | | yes | | `playerView` |
| `GET .../state?role=host` | no | | | yes | `hostView` |
| `POST .../action` host types | no | | no | yes | `HOST_ACTIONS` set, hostId check inside `mutate` |
| `POST .../action` `ready`, `ballot`, `removePhoto` | no | | yes | no | `authPlayer` |
| `POST .../photo`, `GET .../photo` | no | | yes (own only) | no | consent header, lobby/cards phases only |
| `POST .../media/run` | no | | **yes today** | yes | Should be host or worker only (finding F6) |
| `GET .../media/{id}` | yes | yes | yes | yes | generated art only, id is 64 bits random |

Principle: authorisation is decided from server state (`room.hostId`, `room.players[].token`), never from a client supplied role. The `role` query parameter selects a projection and the projection is then authorised; it does not grant anything.

## 3. Session and token design review (findings)

Line numbers as first read (files are being refactored by W3/W4; search the quoted code).

| # | Finding | Where | Severity | Fix | Owner |
|---|---|---|---|---|---|
| F1 | Player token compared with `!==`, not constant time. Same in the media run route `p.token === tok` | `engine.ts:348` (`authPlayer`), `media/run/route.ts:16` | Low (144 bit token, network jitter swamps timing) but trivially fixed | Use `safeEqual` from `lib/security/safe-compare` | W4, W5 |
| F2 | Player token stored in plaintext in the Room record, so anyone with store read access can impersonate every player | `engine.ts:59` | Medium | Store `sha256(token)`; compare hashes with `safeEqual`; token shown once at join | W4 |
| F3 | Token never expires or rotates; there is no re-issue path, and a kicked player's token dies only because the player row is removed | `engine.ts:59`, `action/route.ts:44` | Low | Tokens expire with the game (24 h TTL); add rotate on rejoin | W4 |
| F4 | Token sent in custom headers on every poll (`x-player-token`), so it is in every request log if a proxy logs headers | `state/route.ts:20` | Medium | Logger and ingress redaction (documented below); optionally an `HttpOnly` cookie for same-origin web, header for native later | W7, W9 |
| F5 | Override check increments `failedOverrides` per room, and a new game resets nothing for the host: an attacker host can create many rooms and brute force each (only useful for their own rooms, so low impact); but the minimum length of 4 (`createRoom`) gives a weak space and `hashCode` lowercases and trims, reducing entropy | `engine.ts:28,16,231-244` | Medium | Min 6 chars, keep case, `minOverrideCodeChars` in limits, lock also on host id | W4 |
| F6 | Any joined player can call `media/run`, triggering paid generation | `media/run/route.ts:14-17` | Medium | Host only (or a worker with a service token). Player check also skips `authPlayer` | W5 |
| F7 | `trustHost: true` accepts any Host header; with a mis-set ingress this enables host header injection in callback URLs | `auth.ts:38` | Medium | Set `AUTH_URL` and drop `trustHost` in production, or keep it only behind a proxy that rewrites Host | W7/W8 |
| F8 | Auth.js JWT session has default 30 day lifetime for what is a 2 hour party tool | `auth.ts:37` | Low | `session: { maxAge: 8 * 3600, updateAge: 3600 }` | W7 |
| F9 | Host id for the dev provider is `dev:${name}`, so anyone typing the same name is the same host. Dev only (guarded by NODE_ENV and flag) | `auth.ts:14-23` | Low | Assert `ALLOW_DEV_LOGIN` is unset in chart values and in a CI test | W9 |
| F10 | `GET /state` returns `{unchanged:true}` before authentication when versions match, so an unauthenticated caller can confirm a code exists and read the current version number. Version is not secret, but the 404 vs 200 gap is an enumeration oracle | `state/route.ts:11-14` | Low | Authorise role first for host/player; keep screen cheap; uniform 404 | W4 |
| F11 | Request bodies cast, never validated; non-object JSON (`null`) crashes with 500 | `action/route.ts:25`, `join/route.ts:9`, `rooms/route.ts:11` | Low | Central `parseJson(req, schema, maxBytes)`; map to 400 | W4 |
| F12 | `GET photo` skips the shared error handler and returns `e.message` for unexpected errors | `photo/route.ts:41` | Low | Use `handle()` | W4 |
| F13 | Photo route allocates the whole body before the size check | `photo/route.ts:18` | Medium (memory DoS) | Check `Content-Length`, cap stream | W4 |
| F14 | Orphan photo blob if the later `mutate` fails (put before commit), and key built from `code` | `photo/route.ts:23-25` | Low | Write after commit or sweep by prefix; use tenant key | W3, W4 |
| F15 | `deletePrefix(".")` deletes the whole local media root; single file delete leaves `.mime`; S3 delete not paginated | `media-store.ts:11,31,54` | Medium (data loss, retention) | Tenant key builder, exact prefix, pagination | W3 |
| F16 | Host free text keeps newlines, enabling prompt section forgery; model output not length checked | `sanitize.ts:3-4`, `gm-ai.ts:46-57,82` | Medium | see threat-model M2, M3 | W4, W5 |
| F17 | Media responses use `Cache-Control: public` for per game content | `media/[id]/route.ts:11` | Low | `private` unless a CDN keys by game; confirm with product | W4 |
| F18 | MemoryStore and `globalThis` singletons mean a multi pod deployment with `STORE_ADAPTER=memory` silently splits games across pods | `store.ts:57-63` | High if misconfigured | Refuse to start with `memory` when `NODE_ENV=production` and `CELL_ID` is not `local-0` | W3 |

Session design to adopt: host session = Auth.js JWT, `httpOnly`, `Secure` behind TLS, `SameSite=Lax`, 8 hour max age; player credential = random 144 bit token delivered once at join, stored hashed, sent in `x-player-token`, valid for the game's life, revoked on kick and on deletion. The middleware enforces `Origin == Host` on cookie-capable state changing calls so Lax is not the only CSRF barrier.

## 4. Rate limiting design

Implemented in `lib/security/rate-limit.ts` (token bucket, injectable clock, bounded LRU of keys) and wired in `middleware.ts` through `lib/security/edge.ts`.

- Two scopes per request: `ip:{addr}` and, for game routes, `game:{CODE}`. A request is admitted only if both buckets admit it. Denied requests do not consume tokens.
- Route classes: `state`, `action`, `join`, `photo`, `mediaRun`, `mediaGet`, `create`, `auth`, `api`. Rules in `RATE_LIMITS` (`limits.ts`), rationale in `scale/limits.md`.
- Response: 429, JSON `{error}`, `Retry-After` seconds, request id header.
- IP: the entry added by the last trusted proxy (`TRUSTED_PROXY_HOPS`, default 1), never the leftmost `X-Forwarded-For` entry which a client controls.
- Never limited: `/api/healthz`, `/api/readyz`, static assets, pages.
- Scope of enforcement: per pod (in memory). With N pods and no stickiness the effective limit is up to N times the nominal one. That is acceptable as the first line of defence; the shared backend interface (`RateLimiter`) lets a Redis or sidecar implementation replace it with no caller changes. Ingress-level limits (NGINX `limit_req`, cloud WAF) are the outer layer and are specified in W9's chart values.
- Client behaviour contract (W7): on 429 honour `Retry-After`, then back off polling to at most 10 s; never retry faster.
- Flag: `RATE_LIMIT=off` disables (tests, load generators that do their own pacing).

## 6. CSRF stance

- Player and screen routes authenticate by custom headers (`x-player-token`), which a cross-site form cannot set, so they are not CSRF-able.
- Host routes use a cookie. Defences, in layers: `SameSite=Lax` (Auth.js default), the middleware Origin check (a browser POST carrying `Origin` that differs from `x-forwarded-host` or `Host` gets 403), JSON bodies only, and CSP `form-action 'self'`. Auth.js has its own CSRF token for its endpoints.
- Requests with no `Origin` header (curl, mobile app, server to server) pass this check and rely on the credential.
- Do not add GET endpoints with side effects.

## 7. Input validation

- Every route validates with a schema, rejects unknown fields, caps body size (`maxJsonBodyBytes` 32 KiB; photo 2 MiB) before parsing, and returns 400 with a generic message.
- Strings: trim, strip control characters except `\n` only where multi line is intended (backstory); host prompt fields single line.
- Identifiers: `code` `^[A-HJ-NP-Z2-9]{6}$` after upper casing (today 4 chars); ids `^[A-Za-z0-9_-]{4,40}$`.
- Numbers: clamp as `sanitize.ts` does (good pattern, keep).
- Files: size cap, magic bytes, decode and re-encode (strips EXIF and polyglots), moderation, consent.
- Model output is input: schema validate, length cap per field, strip markup, fall back to the sample case (CONTRACT rule 5).
- Output encoding: React text nodes only.

## 8. Logging policy

Use `createLogger()` from `lib/security/logger` for every log line. It writes one JSON object per line to stdout, redacts by key, scrubs secrets from free text, truncates strings to 2,000 chars, bounds depth and key counts, and never throws.

Never log: override code (any field named `code` in an override body, anything containing `override`), player tokens, session cookies, `Authorization`, API keys, DB URLs, photo bytes or keys, case truth (`killerId`, `truth`, `nudges`, `advanced`, `card`), player backstory text, model prompts and outputs (debug level only in dev, and still redacted), full request bodies.

Always log: `requestId`, `cellId`, `gameId`, route class, status, duration, error class (not message from user input), limiter denials (count by class), AI queue depth and wait. Level via `LOG_LEVEL`. Ingress access logs must drop the `x-player-token`, `x-player-id`, `cookie` and `authorization` headers and the query string on `/api/rooms/*/state`.

Adoption: replace `console.error(e)` in `http.ts` and `console.warn` in `gm-ai.ts` with the logger (W4, W5). Test: capture logs for a full game run and assert no canary appears (tenancy.md section 7).

## 9. Audit events

Structured events, one log line each, `event` field, no payload secrets, retained 30 days (`auditRetentionDays`) in the cell log stream:

`game.created`, `game.started`, `game.ended`, `game.deleted` (with object counts), `player.joined`, `player.kicked`, `override.attempt` (result `ok|bad|locked`, never the code), `override.used` (cmd), `photo.uploaded` (consent type, size), `photo.deleted` (reason), `budget.cap_changed`, `ai.call` (adapter, tokens, cost, queue wait, result), `ai.fallback` (reason), `limiter.denied` (class, scope, sampled), `auth.login`, `auth.denied`.

## 10. Dependency and image scanning, SBOM

CI gates (W8 implements, W10 specifies): `npm ci --ignore-scripts`; `npm audit --omit=dev --audit-level=high`; gitleaks; Trivy or Grype on the built image failing on fixable high/critical; CycloneDX SBOM from `npm sbom` and from the image (Syft) stored with the build; cosign signature on the image digest; Helm chart linted with kubeconform and a policy check (Kyverno or conftest) for the pod rules below. Base image pinned by digest and rebuilt weekly. The root scaffold with Express dependencies is excluded from every build context.

## 11. Least privilege for pods

- `runAsNonRoot: true`, fixed uid 10001, `readOnlyRootFilesystem: true` (writable `emptyDir` for `/tmp` and `.next/cache` only; local file adapters mount their own volume), `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`, no `hostPath`, no `hostNetwork`.
- `automountServiceAccountToken: false` unless workload identity needs it; ServiceAccount has no Kubernetes RBAC.
- Resource requests and limits on every container; PodDisruptionBudget; topology spread over zones.
- NetworkPolicy default deny; egress only to the state store, blob endpoint, AI endpoint and DNS; ingress only from the ingress controller. Block `169.254.169.254` except via workload identity paths.
- Cloud IAM scoped to `{cell}/*` (tenancy.md section 6). DB role: DML on game tables only, no DDL.
- Namespace per cell with Pod Security Admission `restricted`.

## 12. PII and child data policy

- Data we hold: display names (chosen, may be a first name), age group, optional backstory text, optional photo, consent flag, host email via OAuth.
- Minimise: no surnames asked, no birthdates (age group only), no analytics or third party scripts, no external fonts or CDNs.
- Retention: games and everything in them 24 h by default (`GAME_TTL_HOURS`, max 72); photos deleted when avatar generation completes or at 24 h, whichever is first; audit events 30 days without personal text; host email kept while the account exists.
- Consent: photos require explicit consent, guardian consent for under 18, recorded as `self|guardian` on the player; the host sees only `hasPhoto`.
- Access: photos are visible to the uploading player only (preview) and to the image model during a job. Never in any other view, never public.
- Deletion on request: player can remove own photo immediately; host can purge all photos; operator tool `deleteGame`. Verified deletion per tenancy.md section 5.
- Children: no accounts for children (guests only), no free chat between players, no contact data collected, generated content G-rated.
- No selling or sharing, no training on game data. Cloud AI endpoints must be configured with data retention off; photos stay local unless a game opts in.
- Regional: a game's data stays in its cell's region.

## 13. Incident response basics

1. **Detect**: alerts on sustained 429 or 5xx rate, auth failures spike, `override.attempt` locked spike, egress to unknown host (NetworkPolicy deny logs), image scan finding, secret scanner hit, budget alarm on AI spend.
2. **Triage** (15 min): scope by cell. Is truth leaking (secrecy breach), are photos exposed, is it availability only? Page owner W-role by area (security.md owners in the threat model).
3. **Contain**: drain the cell (stop placement, section 8 of `scale/capacity-model.md`), rotate the affected secret, revoke the token (kill games), set `RATE_LIMIT` stricter via config, disable photo upload with a config flag, disable cloud AI.
4. **Eradicate and recover**: patch, rebuild, redeploy by digest to one cell first.
5. **Notify**: if child photos or PII were exposed, notify affected hosts promptly and regulators as the law requires (GDPR 72 hours, COPPA/state law as applicable); legal owns the decision, engineering supplies the facts (game ids, counts, time window) from audit events.
6. **Learn**: blameless review in `docs/platform/reviews/`, one regression test per root cause, update the threat model.
7. **Drills**: tabletop twice a year. Keep an operator runbook: "delete game X", "purge photos for cell Y", "rotate AUTH_SECRET", "drain cell Z".
